## 1. 项目概况

### 1.1 系统定位

WellRead 是面向银联商务(支付领域)的企业级知识库管理系统,由两套系统组成:

- **app/**: 基于开源项目 **WeKnora**(腾讯)v0.8.0 的分支。Go 后端 + Vue3 前端,提供完整的知识库管理、会话问答、Agent、多租户、RBAC 等平台能力。
- **YLSW_RAG/**: 自研的全链路 RAG 检索服务(Python/Flask)。面向支付领域文档深度定制(法规按条切分、元数据过滤、Text-to-SQL 表格查询),承载了竞赛期的完整检索+生成链路。

当前系统处于「竞赛原型 → 企业级系统」的过渡期:双系统并存,app 已通过 `internal/fusion/` 胶水层将问答转发到 YLSW 引擎,但数据面、接口契约、部署形态尚未真正统一。

### 1.2 总体架构

```
┌───────────────────────────────┐
│  frontend (Vue3 + TDesign)    │
└──────────────┬────────────────┘
               │ HTTP/SSE
┌──────────────▼────────────────┐         ┌──────────────────────────┐
│  app (Go, WeKnora v0.8.0)     │  SSE    │  YLSW_RAG (Flask)        │
│  - 知识库/文档管理             │────────▶│  - 4路混合召回            │
│  - 会话/Agent/MCP/IM/数据源    │ /chat/  │  - RRF + BGE 重排         │
│  - 多租户/RBAC/审计            │ stream  │  - DeepSeek 生成          │
│  - docreader (Python gRPC)     │         │  - FAISS + MySQL         │
│  - PostgreSQL + Redis          │         │  - Text2SQL 表格查询      │
└───────────────────────────────┘         └──────────────────────────┘
```

### 1.4 YLSW_RAG/ 服务(自研)

**技术栈**: Python 3.12 + Flask;MySQL 8.4(文档/chunk/表格存储)+ FAISS HNSW(dim 768,截断自 1024,M=32,efSearch=40)向量索引。

**核心管线**(`src/app.py` `_run_query`):

```
用户问题
  → 实体检测 → 规划器(tag + 计划:单跳/并行子问/多跳)
  → 4 路并行召回:
     1. FAISS 语义检索(top50)
     2. BM25 关键词检索(jieba + rank_bm25,top50)
     3. 元数据/产品实体精确过滤(Tier 1)
     4. Text-to-SQL 表格查询(tables_structured)
  → RRF 融合(k=60)
  → BGE reranker 重排(按来源配额:meta≤3/5,语料其余;章节覆盖贪心去重)
  → parent-context 组装
  → DeepSeek-V4-Flash 流式生成
```

**检索分块策略**(`src/ingest/chunker.py`): 按文档类型差异化——法规按「第X条」切分、手册按章节标题树切分、新闻整篇、xlsx 走结构化表格。Parent-child 架构:child 约 300 token,parent = child + 前后邻块。

**摄取管线**(`src/ingest/`): 文件命名即元数据(`TYPE_DATE_ORG_PRODUCT_TITLE_VERSION_ZH.ext`),`doc_classifier.py` 定义七类前缀(REG 法规 / MAN 手册 / PDT 产品 / RPT 报告 / NWS 新闻 / TBL 表格 / GEN 通用),`metadata.py` 从文件名提取文号/机构/日期/产品。

**知识数据**(`Data/`): 120 篇支付领域文档(1.4 MB)——REG 57 / NWS 25 / MAN 19 / PDT 13 / RPT 4 / TBL 2。

**模型接入**(`src/config.py`): BGE-M3 嵌入、BGE-reranker-v2-m3 重排、DeepSeek chat、Qwen-VL 多模态,支持 `gateway`(http://180.76.46.222:8289/v1)与 `local`(Ollama / models/ 目录本地 bge-m3 2.27GB)双后端。

**部署**: Dockerfile(python:3.12-slim + torch CPU)+ entrypoint.sh(等 MySQL → 建表 → 幂等摄取 → 重建索引 → 预热模型 → 起服务);docker-compose = MySQL 8.4 + app(端口 6151)。

**测试**(`test/`): Stage_1 延迟/吞吐、Stage_2 检索评估(MRR/PR/噪声)、Stage_3 LLM-as-judge 答案评测。

## 2. 改造方案

### 2.1 改造目标

1. **整合**: app 的 RAG 线路(检索+生成)整体替换为 YLSW_RAG 引擎,app 保留文档管理、会话、前端等平台能力。
2. **融合取优**: 文档解析(docreader)与领域切分(YLSW chunker)取长补短。
3. **增删优化**: 融合完成后对 app 功能板块做增删与优化,裁剪冗余代码与文件。

### 2.2 数据流改造:app 为唯一文档入口

**方案**: app 上传文档 → docreader 解析 → 推送 YLSW 摄取 API 重新切分建索引。YLSW 按 `knowledge_base_id` 过滤检索范围。

**改动点**(2026-10-13 已实施):

| 系统 | 改动 | 状态 |
|------|------|------|
| YLSW_RAG | ① 新增 `POST /ingest`:接收 app 推送的解析后 markdown + 元数据(含 KB ID);② chunks/documents 表增加 `knowledge_base_id` 字段(documents 另加 `source_doc_id` 幂等键,重复推送=删旧重建);③ 检索层按 KB ID 白名单过滤(融合后统一过滤,SQL 路因无 kb 语义在 KB 过滤时自动不参与);④ `POST /delete_document` 删除同步(MySQL 级联 + chunk_store/BM25 内存重载,FAISS HNSW 残留向量靠检索层过滤+rebuild 清理) | ✅ |
| app | ① 文档上传解析完成后,调用 YLSW `/ingest` 推送(文件/URL 走 ProcessDocument 尾部,手动内容走 triggerManualProcessing);② 文档删除时同步调 `/delete_document`;③ 上传时提取 UMS 元数据(`service/ums_metadata.go` 的 ExtractUMSMetadata)随文档传入 | ✅ |

**设计决策**:
- 多 KB 隔离(事项 A)落地为方案 1:MySQL 加 kb 字段 + 检索后白名单过滤(KB 数量少,方案 2 每 KB 独立 FAISS 索引复杂度收益不成比例)
- /ingest 同步嵌入:单文档 chunks 少(1-2 批 BGE API),入库即检索,失败留 pending 由 rebuild_faiss.py 兜底
- 双写过渡:app 原生向量管线暂保留(FAQ/记忆依赖,事项 B 未迁移),推送失败入 asynq 重试任务 + 每日对账兜底,不阻断本地管线;YLSW 不可用不影响 app 文档管理
- v1 推送 markdown 文本;xlsx 走 §2.3 原始文件直推 Text2SQL 链路(已实施)
- 存量数据迁移:离线管线入库的文档 kb 为空,KB 过滤启用后在 app 问答中不可见;需 `UPDATE documents SET knowledge_base_id='<kb-uuid>' WHERE ...` 挂载或经 app 重新上传

**数据面与检索面完善(2026-10-14 grill 对齐)**:

数据层:

| 项 | 定案 |
|------|------|
| ① xlsx 推送 ✅ | 见 §2.3:YLSW `/ingest` 加 `file_bytes`(base64),`_ingest_xlsx` 走 parse_xlsx → tables_structured/schema_registry(两表均加 `knowledge_base_id`);app 侧 xlsx ≤20MB 推原始文件,失败/超限回退 markdown |
| ② 存量挂 KB | 暂缓;后续本机重摄取 Data/ 120 篇,挂 KB 等 app 有 KB 再定 |
| ③ 双写对账 ✅ | 推送失败入 asynq `engine:push_retry` 任务(payload 只带 tenant/knowledge_id/kb_id,worker 重跑 convert→push,MaxRetry 3);YLSW 加 `GET /documents/ids`;app 每日 03:00 cron(`YLSWReconcileService`,仿 Housekeeping 模式,`GAZE_YLSW_RECONCILE_ENABLED` 门控)双向对账:差集重推(非 completed 自动跳过)+ 多余调 /delete_document(no-op 语义已确认)。**2026-10-15 补**:Admin 手动触发端点 `POST /api/v1/system/ylsw-reconcile`(202 accepted / 409 已运行中),`ReconcileOnce(ctx)` 异步执行拒绝重入,路由挂 systemRoutes Admin 组 |
| ④ 重试链 ✅ | app.py daemon 线程每 30min(`REEMBED_INTERVAL_MINUTES` 可配)重嵌 pending chunks,与 /ingest 共用 `_ingest_lock`;rebuild_faiss.py 留作手动工具 |

检索层(2026-10-14 已实施 ✅):

- `/search` 的 kb_ids 过滤已落地(knowledge_base_ids 参数 → RRF 后 `_filter_by_kb`),无需改动
- SQL 路 KB 语义(原缺口:SQL 候选无 kb 字段,KB 过滤启用时被无条件滤掉,xlsx 问答在企业多 KB 场景永远不可用):**行级作用域**——
  - tables_structured 与 schema_registry 均加 `knowledge_base_id`(ingest 写入,存量 NULL 同 chunk 存量坑)
  - `sql_engine.query(question, kb_ids=None)`:kb_ids 非空时,`_table_real_name`/`get_schema_info`/实体值缓存(收费站/运营公司/字段名)全部带 kb 条件(缓存按 kb 作用域分片);kb 白名单全部非法规格 → 入口统一拒执行
  - 确定性模板 SQL(计数/列举/实体定点/字段字典)生成时直接拼 `AND knowledge_base_id IN (...)`
  - LLM 生成 SQL:正则找 `table_name='X'` 条件处注入 kb 子句(字符集白名单校验,等价参数化);缺该条件 → 拒执行返回 None,回落语料检索
  - SQL 候选按 source=="sql" 在 `_filter_by_kb` 保留(查询本身已行级作用域);/search 跳过 SQL 候选、planner 路径 SQL 经 deps kb_ids 透传维持不变
  - 表名按文件名构造(同名文件跨 KB 行级共存安全),行级过滤是唯一正确解
- doc_type:Go 侧 `umsTypePrefixMap` 补 `"PDT": "product"`(YLSW TYPE_PREFIX_MAP 有 PDT,移植漏项),值域对齐;查询侧 TYPE_HINTS 关键词规则维持(软加权)

### 2.3 解析与切分融合取优

**方案**: docreader 负责格式解析(输出 markdown),YLSW chunker 负责领域切分。xlsx 特殊处理,直走 YLSW Text2SQL 链路。

```
上传文件 → docreader 解析(格式层)
   ├─ 常规文档 → markdown → YLSW chunker 领域切分(法规按条/手册按节/parent-child)
   └─ xlsx     → 直送 YLSW 表格结构化管线 → tables_structured → Text2SQL
```

**改动点**(2026-10-14 grill 对齐,已实施 ✅):

| 系统 | 改动 |
|------|------|
| YLSW_RAG | ✅ `/ingest` 增加 `file_bytes`(base64 编码原始文件)与 `_ingest_xlsx` 分支:parse_xlsx → tables_structured + schema_registry(两表加 `knowledge_base_id` 列);xlsx 走 Text2SQL,不产 chunks |
| app | ✅ xlsx ≤20MB 推原始文件(base64);推送失败或超限回退推 markdown(表格降级为文本走常规管线) |

**格式划分**:

- docreader 负责全部常规格式解析(pdf/docx/doc/pptx/html/web/epub/图片/md/txt)
- xlsx 唯一例外:直走 YLSW parse_xlsx(Text2SQL 链路)
- 冷门格式(xmind/mhtml/markitdown/opendataloader)保留不动
- doc_type 判定两侧值域对齐:Go 侧 `umsTypePrefixMap` 补 `"PDT": "product"`(见 §2.2)

### 2.4 检索生成统一:YLSW 侧新增 SSE 接口
