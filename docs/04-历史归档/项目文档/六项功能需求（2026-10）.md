## 2. 需求一: Git 式文档维护

### 2.1 对象粒度(已对齐)

- **分块级为主**: issue/评论/CR 主要挂在 chunk 上(chunk_id 稳定,QA 引用锚点现成,修复定位精确)
- **文档级兜底**: 元数据类问题(文号错、密级错、部门归属错、格式坏)挂文档级 issue
- 评论一律挂 issue 或 CR(不直接挂 chunk,chunk 上的讨论通过 issue/CR 承载)

### 2.2 权限模型(已对齐,复用现有 RBAC,不新增权限维度)

现有 tenant 四级(owner/admin/editor/viewer)+ org 三级(admin/editor/viewer),映射:

| 角色 | 能力 |
|------|------|
| 文档所有者(=上传者 created_by) | UI 标注「所有者」徽标;天然是 editor+ 能力,无额外权限代码 |
| viewer | 提 issue、评论 |
| editor(含 org editor) | 提 CR、直接编辑 chunk(已有 updateDocumentChunk) |
| **owner/admin(tenant 或 org)** | **接受/驳回 CR、关闭 issue**(用户修正:仅 owner/admin,editor 无此权) |
| 评论作者 | 可删除自己的评论 |
| owner/admin | 可删除任意评论、删除 issue |

### 2.3 变更请求(CR)形态(已对齐)

- **PR 式多 chunk**: 一个 CR 可含多个 chunk 的建议(CR 条目列表,每条 = chunk_id + 建议全文)
- **建议全文**: 不实现 diff 算法,提交者直接写整段建议文本
- **审批全有或全无**: 接受 = 全部条目落地;驳回 = 整体驳回;驳回后提交者可修改重新提交(CR 回 open 状态);部分接受靠拆多个 CR 满足
- **落地方式**: 接受后 app 侧 chunks 表逐条更新 content(chunk_id 不变),标记文档待重推,重推 YLSW /ingest(复用现有幂等重建:全文重切分+重嵌)。120 篇规模成本可接受,v1 不做单 chunk 增量端点
- CR 条目记录 original_content 快照(提交时的 chunk 内容),审批时展示新旧对比(组件 diff 高亮,非算法 diff)

### 2.4 状态机(已对齐,手动流转)

- issue: `open` / `closed`(owner/admin 手动关闭)
- CR: `open` / `accepted` / `rejected`(owner/admin 操作,附审批意见 review_comment)
- **接受 CR 时联动提示**: 弹窗列出引用同一 chunk 的 open issue,可勾选批量关闭(人工确认,不自动)
- 不做内容 hash 自动关联(chunk 重切分后 ID 不稳,自动联动误关风险高)

### 2.5 锚点失效策略(已对齐)

- CR 落地只改 content,chunk_id 不变,锚点天然稳定
- 唯一失效场景: 文档重新解析(删旧建新 chunk)。此时挂在旧 chunk 上的 issue/CR 标 `anchor_orphaned`,降级为文档级展示,内容全保留,不自动重匹配
- 重推 YLSW 不影响 app 侧 chunk_id(app 侧切分是权威,YLSW 侧是副本)

### 2.6 UI 落点(已对齐)

- **doc-content.vue 扩展**(3331 行,已具备 chunk 分页浏览/合并视图/编辑/修订):
  - chunk 视图每行加「提 issue」「提 CR」按钮
  - 抽屉顶部加「协作」标签页: 本文档 issue/CR 列表 + 详情线程 + 评论
- **KB 级 issues 聚合页**: 跨文档筛选(状态 open/closed、类型 issue/CR、与我相关),GitHub Issues 列表观感
- GitHub 观感 = 列表页 + 详情页两个视图,不做三栏复杂布局
- CR 详情页: 多 chunk 对比视图(原内容 vs 建议内容,红绿高亮)+ 审批按钮 + 评论线程

### 2.7 QA 联动入口(已对齐,用户补充)

问答引用卡片两个入口:
1. **「反馈此内容」**: 直接弹出预填 chunk 锚点的 issue 抽屉(标题可自动生成「引用内容问题反馈」,正文预填上下文: chunk 片段 + 用户当时的问答)
2. **「打开文档协作页」**: 跳转该文档 doc-content 抽屉 + 协作标签页(用户感知文档质量可能不行时,查看/提交完整变更需求)

### 2.8 IM 通知(已对齐: 群推 + 所有者个人@)

**现状**: IM 模块只有被动回复(SendReply 需 incoming 消息),主动推送是新增能力。

- **新增 outbound 通道**: 各 adapter 新增主动推送接口(企微应用消息推送或群机器人 webhook、钉钉 webhook、飞书 webhook;凭证复用现有渠道配置,补充 webhook/corpsecret 字段)
- **群推**: KB/组织配置默认 IM 群(扩展现有渠道配置),事件推群卡片: 新 issue、新评论、CR 提交、CR 被接受/驳回、issue 被关闭
- **个人@**: ums_employee 加企微 userid 字段(工号↔IM 账号映射);新 issue @文档所有者个人(如已绑定)
- v1 **不做 issue 指派功能**(谁修谁领走,评论区认领)

### 2.9 数据模型草案

```sql
-- 统一评论表(issue 与 CR 共用)
doc_comments: id, tenant_id, target_type(issue|cr), target_id, body,
              created_by, created_at, deleted_by, deleted_at

-- 文档 issue
doc_issues: id, tenant_id, knowledge_id(文档), chunk_id(可空=文档级),
            title, body, status(open|closed), anchor_orphaned(bool),
            created_by, created_at, closed_by, closed_at

-- 变更请求
doc_change_requests: id, tenant_id, knowledge_id, title, description,
                     status(open|accepted|rejected), created_by, created_at,
                     reviewed_by, reviewed_at, review_comment

-- CR 条目(PR 式多 chunk)
doc_cr_items: id, cr_id, chunk_id, original_content(快照), suggested_content,
              seq(排序)
```

关联: 迁移编号顺延(当前至 000101);chunk 删除(重新解析)时按 §2.5 置 anchor_orphaned。

### 2.10 API 草案

| 端点 | 权限 |
|------|------|
| GET/POST /api/v1/knowledge-bases/:kb_id/issues | Viewer+ |
| GET/PATCH /api/v1/issues/:id(关闭) | 关闭仅 Owner/Admin |

## 3. 需求二: 每 KB 语义缓存(常问知识桶)

### 3.1 决策(已对齐)

- **写入**: 全量写入(所有问答对入池),容量上限每 KB 默认 500 条 + LRU 淘汰 + TTL 默认 7 天(均可配)
- **位置**: **YLSW 侧**。/chat/stream 内 query 先算 embedding 查缓存,命中直接返回,跳过 4 路召回
- **范围**: 仅 normal 生成式问答;Agent 检索(/search)、评估、SQL 直查不缓存
- **与 FAQ 关系**: 并存不融合。FAQ = 人工精选条目(现有模块不动),缓存 = 自动问答池,UI 分开

### 3.2 实现要点

- YLSW 新表 `query_cache`: kb_id, question_text, question_embedding(BLOB), answer_json, references_json, sensitivity, department, created_at, last_hit_at, hit_count
- **命中**: 余弦相似度 ≥ 0.92(可配,保守防错答)→ 命中后仍过 `_filter_by_sensitivity`/`_filter_by_kb`/`_filter_by_department`(缓存答案跨用户复用必须重过权限过滤)→ SSE 发 `cache_hit` 事件 + 缓存答案 + 原 references
- **失效**: /ingest 重建文档 → 该文档 chunks 引用过的缓存条目全部删除(检索层有 chunk 映射,现成)
- **SSE 协议**: 新增 `cache_hit` 事件;app 前端状态栏标「命中缓存」+ 提供「重新检索」按钮(绕过缓存强制重查)
- 缓存答案存 JSON envelope(与需求六结构化输出同构,直接兼容)

## 6. 需求五: 多轮指代消解 + 实体锚定

### 6.1 决策(已对齐)

- **实体槽确定性提取**: 从每轮 YLSW 返回的 references 元数据(文号/机构/产品,§2.14 已结构化)+ 用户 query 中识别出的实体(must_keep_tokens)累积;计算式(从会话消息历史推导,messages 表已存 knowledge_references),**不新建持久化**
- **LLM 只做改写**: 输入 = 当前 query + 实体槽 + must_keep_tokens 硬约束,输出 = 完整 query
- **LLM 门控（2026-10-21 用户改定，取代原「检测式触发」）**: 只要会话已有实体槽，就把当前 query 交给 LLM 判定+改写；完整问题由模型原样返回（app 层判为未改写，不发事件、不落库）。不再用指代词规则做门槛——中文指代/省略是开放集合，规则漏检会导致「其第三部分」这类追问完全不触发。代价是每轮追问多一次 LLM 往返（默认 5s 超时，可配；3s 实测偶发超时）
- **位置**: app 侧(UI 可展示「已改写为: …」,用户可修正;修正后按修正版重新检索,修正版按新 query 正常进槽)
- **范围**: 仅 normal 问答;agent 检索用户主导,不做
- **兜底**: LLM 超时/失败 → 原样透传,不阻断问答

### 6.2 关键约束(用户原文强调)

- 改写不得改写标识符: 文号、条款号、产品名必须 verbatim 保留,must_keep_tokens 列表硬约束
- 技术文档场景的 identifier drift 是改写最大翻车点
- YLSW 接收的始终是完整明确的 query

### 6.3 实现要点

- 实体槽结构: entity stack(最近提到的产品/文号/条款/日期,深度默认 10)+ 约束(KB/密级/角色)
- 槽重置: 新轮 query 明确提到新实体时以新实体为主;换 KB 场景清槽
- 改写调用: DeepSeek 小模型,超时 5s 兜底透传;改写结果前端展示为无边框折叠改写卡片,支持原句/实体高亮、锚定来源、跳到出处、原文重搜/编辑改写（详见 `../02-需求与设计/UI设计细节.md` §3.2）

**实施记录(2026-10-21)**: `app/internal/application/service/query_rewrite.go`——实体槽来自历史引用元数据 + 近 3 轮问答摘要（深度 10，过滤文件名型 doc_title/「通用」）；门控按用户 B 决策改为「有实体槽即 LLM 判定+改写」；must_keep（文号/条款/部分·章·节/《》/英文标识/命中槽实体）逐字校验，当前问题未提条款时拒绝改写出新增条款；**禁止从助手回答抄录文号，模型新增的未验证文号在发送前剪除**（实测「其第五条」曾因加入源文档不存在的穗府函〔2025〕220号，把正确 chunk 从第 1 挤到第 3，导致拒答；剪除后恢复第 1 并答出内容）；默认 5s 超时（3s 实测偶发超时），调用失败/校验不过一律原文透传；改写写入 `messages.query_rewritten`（迁移 000103 PG + 000015 SQLite）；SSE `query_rewritten`；仅 `channel=web`。实测：依赖追问改写成功，自包含问题模型原样返回（约 1.7s 门控、无改写块）。

**UI 返工记录(2026-10-21 晚场)**: 用户提供样例图后重做——无边框折叠态「已改写 · 原指代 → 目标实体」，展开态原句橙色下划线/实体绿色高亮/映射行/锚定来源/跳到出处/chips/编辑改写/使用原文检索；LLM 改写 JSON 新增 `source_text`/`target`/`anchor_text`，后端逐字校验后才展示；新增 `messages.query_rewrite_meta` JSONB（迁移 000104 PG + 000016 SQLite）持久化映射/来源/耗时，刷新后保留；跳到出处优先用回答正文中的实体原文，滚动到高亮实体并闪绿 1.2s，旧错误 meta 由前端 target 分段候选回退修复。对话页同时加入用户/回答身份头部（见 `../02-需求与设计/UI设计细节.md` §3）。

## 9. 风险与注意

- **JSON mode 文本质量**: 自由文本答案包 envelope 后质量可能有折损,DeepSeek JSON 输出能力缓解,批3 实测对比后再定阈值
- **IM 主动推送凭据**: 企微应用消息需 corpsecret/agent 权限,群机器人 webhook 更轻,实施时按用户现有凭据选择通道
