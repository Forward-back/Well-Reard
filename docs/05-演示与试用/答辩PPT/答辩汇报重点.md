# WellRead 答辩汇报重点（6 页 · 4 分钟）

> 场景：公司内部汇报 / 立项答辩（纯展示交流，不涉及资源决策）
> 受众：公司领导与业务负责人
> 口径：知识库部分偏业务价值，可适度放大；数字按「真实 + 预估标注」处理
> 主线：每页埋一个差异化点，最终汇成一句话——**企业级知识基础设施 vs 玩具级问答**

## 时间分配

| 页 | 主题 | 时长 | 差异化钩子 |
|---|---|---|---|
| P1 | 封面 · 一句话定位 | 15s | 不是接个大模型，是知识基础设施 |
| P2 | 痛点 · 散、慢、旧、险 | 45s | 聊天机器人一个都解决不了 |
| P3 | 方案 · 一条知识生产线 | 40s | 别的知识库是仓库，我们是生产线 |
| P4 | 差异化① 答得准、有出处 | 50s | 通用 AI 给答案，我们给证据链 |
| P5 | 差异化② 读得深、管得住 | 50s | 从「存和查」到「可经营、可审计」 |
| P6 | 价值收尾 · 三类人受益 | 40s | 知识从「文件」变成「资产」 |

合计 4 分 00 秒。若现场紧张，可压缩 P3 至 30 秒，口播已设计为可裁剪结构。

## P1 封面

**页面标题**：WellRead 企业知识库
**副标题**：让支付知识，查得到、读得懂、管得住
**核心信息**：面向支付机构的私有化企业知识中枢——不是又一个通用 AI 问答。

**汇报要点**
1. 三个关键词立住定位：**私有化、制度级、全链路**。
2. 一句话说清它是什么：把公司制度知识从「文件」变成「随时可用、可信可管的知识资产」。
3. 埋钩子：接下来每页展示一个和通用 AI 的本质区别。

**口播引导（约 15 秒）**
> 各位领导好，我汇报的是 WellRead 企业知识库。一句话：让公司的支付制度知识，查得到、读得懂、管得住。它不是接个大模型做问答，而是一套能在公司内部真正落地的知识基础设施。

**配图建议**：Logo + 主问答界面截图（选带引用上标、答案完整的一屏）。
**差异化金句（可做页面大字）**：通用 AI 只会「说」，WellRead 让知识「可查、可引、可管」。

## P2 痛点：散、慢、旧、险

**页面标题**：支付机构的知识困境，不是缺 AI
**核心信息**：知识本身散、慢、旧、险，缺的是一个企业级的知识底座。

**汇报要点**
1. **散**：制度散落在共享盘、OA、邮件、聊天记录里，找一份文件先问三个人。
2. **慢**：同一个问题反复问专家，专家时间被切碎（*预估：一线员工每周 2–3 小时耗在找资料上*）。
3. **旧**：新旧版本并存，已废止文件仍被引用——这是合规上真正的风险，也是最容易被忽视的。
4. **险**：通用大模型答支付问题靠「编」，没有出处；公有云 AI 数据出域，本身就过不了合规。

**口播引导（约 45 秒）**
> 先看问题。支付机构的知识现状可以概括为四个字。散——制度散在共享盘、OA、邮件和聊天记录里，找一份文件先问三个人。慢——同一个问题反复问专家，专家时间被切碎。旧——新旧版本并存，已废止的文件还在被引用，这是合规上真正的风险。险——通用大模型答支付问题靠编，还没有出处；公有云 AI 数据出域，本身就过不了合规。这四个问题，聊天机器人一个都解不了。我们缺的不是模型，是企业级的知识底座。

**配图建议**：四象限图（散 / 慢 / 旧 / 险），每象限配一个办公场景小图标。
**差异化金句**：缺的不是模型，是底座。

## P3 方案：一条知识生产线

**页面标题**：WellRead 是什么——一条完整的知识生产线
**核心信息**：覆盖「入库 → 问答 → 精读 → 协作 → 治理」五个环节的闭环，六个服务全部本地部署。

**汇报要点**
1. **全链路闭环**：文档进来 → 自动解析打标 → 权限内问答 → 条款级精读 → 协作维护 → 治理审计，五个环节首尾相接。
2. **六个服务全本地**：前端、应用、RAG 引擎、文档解析、数据库、缓存，全部部署在公司内网，数据一步不出域。
3. **自动打标**：部门、文号、机构、产品、密级自动识别，知识一进来就是「可管理」的状态，不靠人工建档。
4. **定位差异**：市面多数知识库只是「存和查」的仓库；WellRead 管的是知识从进来到被用、被维护的全过程。

**口播引导（约 40 秒）**
> WellRead 的做法，是把知识做成一条生产线。文档进来，自动解析、自动打标——部门、文号、机构、产品、密级都识别出来；然后进入权限内的问答、条款级精读、协作维护和治理审计，五个环节形成闭环。整套系统六个服务全部部署在公司内网，数据一步都不出域。市面上的知识库大多只是一个仓库，WellRead 管的是知识从进来到被用、被维护的全过程。

**配图建议**：一张简化架构图——上层五环节闭环横条，下层六个服务方块，标注「公司内网」边框。可参考 `docs/01-项目总览/系统总览.md` 与登录页架构图简化。
**差异化金句**：别人做仓库，我们做生产线。

## P4 差异化①：答得准、有出处

**页面标题**：答案不是「像对的」，而是「有出处的」
**核心信息**：四种找法 + 条款级引用 + 追问锚定 + 检索过程透明，构成完整证据链。

**汇报要点**
1. **四种找法一起上**：语义检索、关键词、元数据标签、表格数据（Text2SQL），制度正文、附件、Excel 里的数据都不漏。
2. **引用到原句**：每个答案标注来源，精确到制度原文的那一句话，可悬浮预览、可一键跳转原文。
3. **听得懂追问**：多轮对话里的「其第三部分」「这个条款」，自动锚定到上一轮的文件和条款，不用重复背景。
4. **过程透明**：检索过程八个阶段全程可见——召回了什么、融合后剩什么、重排后留下什么，一目了然。

**口播引导（约 50 秒）**
> 第一个差异化：答案是得出处的。我们同时用四种找法——语义、关键词、标签和表格数据，制度正文、附件、Excel 数据都不漏。每个回答都标注来源，精确到原文那一句话，点一下就能跳回去。多轮追问里的「其第三部分」，系统会自动锚定到上一轮的文件和条款。更关键的是，检索过程八个阶段全程可见：召回了什么、重排后剩什么，一目了然。通用 AI 给你一个像对的答案，WellRead 给你答案加证据链。

**配图建议**：三张截图横向拼接——① 答案正文带 `[n]` 引用上标；② 引用悬浮卡（标题/机构/日期/版本）；③ 检索过程展开面板（四路召回计数 + 重排 + 生成耗时）。
**差异化金句**：通用 AI 给答案，WellRead 给证据链。

## P5 差异化②：读得深、管得住

**页面标题**：从「存和查」到「可经营、可审计」
**核心信息**：交互式精读 + 公文式协作 + 四层权限 + 治理看板，让知识资产真正被经营。

**汇报要点**
1. **交互式精读**：监管文件逐节读、边读边问、自动记笔记，读完自动生成精读报告，三档深度按需选择（*预估：30 页监管文件从 2 小时缩到 20 分钟*）。
2. **公文式协作**：制度修改像公文流转——提交修改申请、他人审批、合并生效、历史版本可回滚，每次变更都有记录。
3. **权限四层过滤**：六种角色 × 部门 × 知识库 × 密级，四个维度同时生效；没权限的内容在检索阶段就进不来——不是藏起来，是答不出来。
4. **治理有看板**：谁查了什么、哪些知识有缺口、哪些文件已废止，管理端全程可视。

**口播引导（约 50 秒）**
> 第二个差异化：读得深、管得住。监管文件可以逐节精读，边读边问、自动记笔记，读完自动生成精读报告——一份三十页的文件，预估从两小时缩到二十分钟。制度修改走公文式流程：提交申请、他人审批、合并生效、历史版本可回滚。权限上，六种角色、部门、知识库、密级四个维度同时生效，没权限的内容在检索阶段就进不来——不是藏起来，是答不出来。谁查了什么、哪里有知识缺口，管理端都有看板。别的知识库停在存和查，WellRead 让知识资产可经营、可审计。

**配图建议**：三张截图并排——① 精读工作台三栏（阅读区 / 笔记 / 报告）；② 修改申请审批页（合并按钮 + 审批记录）；③ 治理看板或审计列表。
**差异化金句**：知识库的终点不是「查到」，是「管得住」。

## P6 价值收尾：三类人受益

**页面标题**：一套系统，三类人受益
**核心信息**：知识从「文件」变成「资产」，从「个人经验」变成「组织能力」。

**汇报要点**
1. **一线员工**：制度秒查、答案带出处（*预估：找制度从 15 分钟到 15 秒*）。
2. **合规与专家**：监管文件精读报告自动成稿，专家从「人肉检索」中解放（*预估：重复答疑减少一半以上*）。
3. **管理层**：知识资产有版本、有审阅、有审计、有看板，合规风险可控。
4. **已验证**：六个角色全链路、120 篇制度文档测试集入库问答、精读 / 协作 / 治理闭环全部跑通；下一步接入更多业务域，并通过 MCP 对接业务系统。

**口播引导（约 40 秒）**
> 最后是价值。一线员工查制度从十五分钟到十五秒；合规和专家从人肉检索里解放出来，预估重复答疑减少一半以上；管理层看到的是一套有版本、有审计、风险可控的知识资产。目前六个角色全链路、一百二十篇制度文档的入库问答、精读协作治理闭环都已经验证跑通。下一步接入更多业务域，通过 MCP 打通业务系统。让支付知识，查得到、读得懂、管得住——这就是 WellRead。谢谢大家。

## 追问预案（Q&A 备用）

1. **精读和直接把文档丢给通用 LLM 有什么区别？不就是加了一段提示词？**
   提示词只规定「怎么读」，管不住三件事：**记得住**（每轮术语/结论/问题/矛盾落库，下一轮从库里重组，可停可续可复现）、**验得准**（每条结论带可定位出处，矛盾必须双出处，过不了引用充分/无冲突/跨文档一致三道门就不算结论）、**管得了**（文档不出域、权限在检索阶段生效、全程可审计）。一句话：通用 LLM 是「会读的人」，WellRead 是「带档案室、审批流和质检线的阅读车间」——读法能抄，车间搬不走。
   追问「现在做到哪一步」：逐轮阅读、停止恢复、引用定位、权限复核、审计、导出已跑通；状态四表化与三道门收敛是下一版重点。
   追问「没有 Claude Code 那样的 agent 生态，凭什么接近 agent + skill？」：那个 skill 真正依赖的只有四件事——选读原文、范围内检索、状态外置、逐轮推进；我们用窗口取文、文档内检索、四张结构化表、引擎五拍状态机对应，并加轮内有界检索循环（≤3 次）。生态宽度决定「能做什么」，精读效果取决于「记得住、验得准、按轮推进」；前者主动不要，后者用工程补齐。真实差距在模型上限，用专用阅读模型 + 三道门 + 人工确认兜底。
2. **数据安全怎么保证？**
   六个服务全部本地部署、数据不出域；检索强制带权限范围，没权限直接拒答；审计只存问题哈希不存原文；密钥只显示掩码。
3. **大模型编造怎么办？**
   每个答案带原文引用，检索过程可展开复核；查不到就明确说查不到，不硬答。
4. **知识更新怎么维护？**
   文档修改走「申请—审批—合并」流程，版本可回滚；新版本入库后旧版本自动标记废止，检索时降权。
5. **推广成本高吗？**
   整套容器化部署，六个服务一条命令起停；接入新部门只需建知识库、传文档，标签自动生成。
