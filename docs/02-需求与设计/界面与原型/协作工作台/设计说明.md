# 协作工作台设计说明

> 状态：优化中
> 最后更新：2026-10-26
> 目标读者：前端、产品、设计
> 关联：[协作与版本控制](../../功能与交互/协作与版本控制.md)、[界面规范](../界面规范.md)

## 1. 设计原则

轻量 GitHub 模型：文档不引入分支。文档只有一个“当前发布版”，变更请求（CR）基于当前版本拍快照，审批通过后由 manager 合并并生成新版本。保留 diff、审阅、追溯、回滚，去掉分支与冲突合并的复杂度。

| GitHub 概念 | 本系统对应 |
|---|---|
| Repository | 知识库 |
| File | 文档 |
| Branch | 不引入；用“当前版 + CR 快照”替代 |
| Commit | 版本 V1.x；合并 CR 自动递增 |
| Pull Request | 变更请求（CR） |
| Issue | 问题；支持锚点评论 |
| Review / Merge / Revert | 审阅 / 合并 / 回滚 |

状态机：草稿 → 待审阅 → 修改中 → 已合并 / 已关闭。所有列表使用统一徽章：绿色=开放、紫色=已合并、灰色=已关闭、琥珀=需行动、虚线=草稿。

## 2. 信息架构

```text
知识库列表页
 └─ 文档列表
     └─ 文档详情抽屉（右侧）
         ├─ Tab1 文档内容   ← 选区工具条、锚点评论
         ├─ Tab2 协作       ← issue 列表、新建 issue、新建 CR
         └─ Tab3 版本       ← 版本时间线、对比、回滚
整页路由：
  /kb/:kbId/doc/:docId/cr/new        → 变更请求工作台
  /kb/:kbId/doc/:docId/cr/:crId      → 变更请求详情
  /kb/:kbId/doc/:docId/versions      → 版本历史（抽屉 Tab 数据源）
```

硬接线：

- 工作台提交成功 → 跳转 CR 详情。
- CR 详情右侧版本徽章 → 版本历史并定位版本。
- issue 的“转为变更请求” → 工作台并预填锚点与描述。

## 3. 原型文件

| 文件 | 内容 | 落位 |
|---|---|---|
| `协作入口.html` | 选区工具条 / 新建问题 / 我创建的 | 拆分嵌入文档内容 Tab、协作弹窗、协作列表 |
| `变更请求工作台.html` | 三栏 + 双栏对照 | 整页；替换旧“新建变更请求”弹窗 |
| `变更请求详情.html` | 对话 + diff + 审阅侧栏 | 整页；协作主战场 |
| `版本历史.html` | 版本时间线 + 任意对比 + 回滚 | 文档抽屉 Tab3 |

## 4. 关键交互

- 入口层：选区后出现轻量工具条；issue 支持评论、关闭/重开、转 CR。
- 工作台：左侧文档结构，中部编辑与 diff，右侧审阅者/状态/提交动作；草稿可恢复。
- 详情：变更 diff、审阅者、审批状态、评论、合并/关闭动作；只读用户不显示提交/审批/合并按钮。
- 版本：时间线 + 版本对比 + 回滚；回滚生成新版本，不删历史。
- 状态标签必须诚实：待审/已通过/需修改/已合并/已关闭，不用“处理中”模糊表达。

## 5. 数据与边界

- 正式内容只通过 CR 合并；直接编辑不覆盖正式版本。
- 仅 manager 可合并；审批通过不等于合并。
- 合并前至少一名其他审阅者/部门审计员批准；提交人不能审批自己的 CR。
- 部门审计员可审批/驳回本部门 CR；单 CR reviewer 只对该 CR 生效。
- 审阅意见与文档选区/chunk 绑定；chunk 锁只提示并发，不是硬性排他锁。
- 版本与 chunk/引用关联，便于追溯答案依据。
- 详细权限规则见[协作与版本控制](../../功能与交互/协作与版本控制.md)。
