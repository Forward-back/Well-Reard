# 角色生态位规定

> 状态：当前
> 最后更新：2026-10-26
> 目标读者：产品、开发、测试、运维
> 关联：[能力与路由矩阵](能力与路由矩阵.md)、[共享空间与ACL](共享空间与ACL.md)、[部门管理工作台](../功能与交互/部门管理工作台.md)、[系统运维台](../功能与交互/系统运维台.md)

本文是角色定位、权限边界与验收口径的权威文档；能力码以 `app/contracts/capabilities.json` 为唯一事实来源，本文 §8.4 为当前快照。

## 1. 总原则

- 本项目是公司内部单租户本地部署，不按 SaaS 多租户运营设计。
- 角色按生态位拆分，不按“权限多少”简单堆叠；同一账号可以持有多个身份，但各身份的能力不互相穿透。
- UI 是能力契约的投影：菜单、路由、控制台分区都从 caps 派生，不在页面内写角色 if-else。
- 技术运维与公司业务治理分离：系统管理员负责底座和运行，公司管理员负责人和业务。
- 高风险动作必须二次确认并写审计：授予/撤销系统管理员、重置密码、删除平台 API Key、清理归档任务、修改系统级配置。

每个角色一个固定开发测试账号，统一密码 `Admin123!`；仅用于本地开发与截图，不用于生产。

| manager | `role_manager@example.com` | `Admin123!` | 默认部门 manager |

## 2. 系统管理员（system_admin）

### 2.1 一句话定位

公司内部的技术总运维：保证系统装好、跑稳、模型与解析可用、队列与密钥安全；不参与公司业务治理。

system_admin 不是“超级管理员”：不进入知识库、问答、精读、共享空间；不分配公司/部门角色；不接触公司治理数据，`/ops` 只看技术状态和账号元数据。

### 2.2 职责边界

负责：

- 应用运行状态、版本、启动时长、数据库迁移状态。
- 模型、Ollama、解析器、存储、向量引擎等技术与连接配置。
- API、CLI 集成配置；IM 管理面已下线。
- 运行队列、worker/模型并发、失败任务与归档清理。
- 平台 API Key、系统审计、SSRF 白名单等安全项。
- 账号救援：用户查询、创建身份、重置密码、授予/撤销系统管理员。
- 单租户空间默认配额、注册规则、未归类系统配置。

不负责：

- 知识库、文档、对话、共享空间的日常使用与业务内容管理。
- 成员邀请、部门归属、公司角色分配；这些归 company_admin。
- 公司治理看板、公司业务审计；这些归 company_admin。
- 技能目录与技能授权；由部门 manager / knowledge_admin 维护，company_admin 只读。

只读元数据例外：集成作用域选择需要知识库/智能体名称，运行统计需要消息索引计数；这些接口只返回名称、ID、计数等元数据，不返回正文或会话内容。

### 2.3 能力与数据范围

- system_admin 的独立能力以 `settings:system_manage` 为核心，并获得全部技术配置能力：
  `settings:models_manage`、`settings:infrastructure_manage`、`settings:integrations_manage`、`settings:workspace_manage`。
- company_admin 不再拥有上述技术配置能力，只保留成员、部门、公司统计/审计；技能目录全部部门只读。
- 单租户部署下，技术配置使用“隐式唯一空间”上下文：system_admin 不需要公司 membership；后台自动取唯一空间作为配置目标，但不授予知识库、对话、共享空间等业务路由。
- 双身份规则：如果 system_admin 同时被邀请为公司成员，公司侧权限只按该 membership 的公司/部门角色计算；system_admin 身份不额外授予任何公司业务能力。
- system_admin 可授予/撤销其他系统管理员，但不能借此获得公司业务权限。
- 技术配置使用隐式单租户上下文：`users.tenant_id` 指向唯一空间；系统管理员不需要 `tenant_members` 行，后端以内部 `ops` 角色提供租户上下文，该角色低于 viewer，不能通过任何业务路由。

### 2.4 UI 形态

独立浅色运维工作台，不复用公司工作台的侧栏和内容导航。

- 路由命名空间：`/ops/*`；默认登录落地 `/ops/overview`。
- 外壳：左侧运维导航（七个分区）+ 顶部状态栏（版本、运行时长、最近刷新时间、手动刷新）+ 内容区。
- 品牌：沿用 WellRead 字体、绿色主色；状态用健康色点区分，不引入全暗色监控屏。
- 头像菜单：身份信息、切换到公司工作台（仅双身份可见）、设置（偏好 + 账户 + 版本）、退出登录。
- 公司工作台不再出现“平台管理”侧栏入口；系统管理员只从运维工作台进入技术配置。

#### 七个一级分区

1. 总览
2. 模型与引擎
3. 集成
4. 运行队列
5. 安全与审计
6. 账号运维
7. 系统设置

#### 总览页

两栏主次布局：

- 顶部运维待办条：按 P1/P2/P3 汇总当前派生的活跃告警；无告警时显示“全部正常”。
- 五张健康卡：应用、解析、存储、模型、队列；附依赖与最近检查时间。
- 队列区：待处理/执行中/重试/归档四格实时数字 + 最近 2 分钟负载趋势；不再使用混合语义的环形图。
- 资源水位：存储、待处理队列、归档任务三条进度条，带阈值红线。
- 模型通道：按供应商聚合已配置模型；测试按钮跳转模型与引擎页手动测试。
- 右侧：当前告警与最近平台审计；审计显示操作人、可读动作、对象详情与时间。
- 底部动作型快捷入口：刷新状态、处理队列任务、测试模型连通性、查看安全与审计。
- 顶部显示 DEV/PROD 环境徽章、已运行时长、健康检查周期与最近刷新时间。
- 首版不新增监控表：告警从当前健康状态实时派生；队列趋势为前端最近 2 分钟滚动窗口；不展示虚构的 24h 趋势或通道延迟。

健康卡口径：

- 应用：版本、启动时长、DB 迁移状态。
- 解析：DocReader 连接状态、可用解析引擎数量。
- 存储：当前启用后端、可用性。
- 模型：默认/已配置模型数量、向量引擎、Ollama 配置状态。
- 队列：待处理、重试、失败数量。

#### 分区内容

| 分区 | 内容 | 数据/能力 |
|---|---|---|
| 总览 | 五健康卡、三实时图表、最近异常、快捷入口 | `settings:system_manage` + 技术配置只读 |
| 模型与引擎 | 模型管理、Ollama、解析引擎、存储后端 | `settings:models_manage` / `settings:infrastructure_manage` |
| 集成 | API、CLI 接入（IM 管理面已下线） | `settings:integrations_manage` |
| 运行队列 | 队列状态、任务操作、worker/模型并发参数 | `settings:system_manage` + `settings:workspace_manage` |
| 安全与审计 | 平台 API Key、系统审计、SSRF 白名单 | `settings:system_manage` |
| 账号运维 | 用户目录、创建账号、重置密码、系统管理员授予/撤销、注册规则 | `settings:system_manage` |
| 系统设置 | 空间默认配额、版本与系统信息、未归类配置 | `settings:system_manage` |

### 2.5 登录与双入口

- 登录后默认进入 `/ops/overview`，即使账号同时拥有公司 membership 也不先进入公司工作台。
- 只有同时拥有有效公司 membership 时，头像菜单才显示“切换到公司工作台”；无 membership 时不显示。
- 公司工作台 → 运维工作台使用同一头像菜单的“切换到运维工作台”入口。
- 切换只改变当前工作台路由和导航，不改变 token 或 principal；公司侧仍按 membership caps，运维侧按 system_admin caps。
- 直接输入公司业务 URL 时，若没有对应 membership caps，仍进入 403。

### 2.6 账号运维边界

- company_admin 继续按邮箱邀请同事并分配部门/公司角色。
- system_admin 负责账号救援：查询用户、创建身份、重置密码、授予/撤销系统管理员。
- system_admin 不修改用户的公司角色、部门归属和成员状态。
- 新增用户目录：邮箱/用户名/状态/是否系统管理员，可搜索；在行内提供重置密码、授予/撤销系统管理员、创建账号。
- 用户目录只返回账号运维所需字段，不返回知识库、对话、部门业务数据。

### 2.7 开发与验收

已实施（2026-10-25）：

- `/ops` 独立布局与七个分区路由。
- 运维待办/告警、五健康卡、队列分格与资源阈值、模型通道、可读审计与动作快捷入口。
- 技术配置组件从 Settings 弹窗迁移到运维工作台。
- 平台 API Key、系统审计、系统设置、账号运维组件重组。
- 用户目录后端查询接口与前端页面（`GET /api/v1/system/admin/users`）。
- system_admin 隐式单租户上下文（内部 `ops` 角色，无 membership 行）。
- 双入口头像切换与登录落地。
- 能力矩阵、Settings 导航、菜单与 403 同步调整。
- 验证：system_admin 七个页面无 4xx；业务 URL 返回 403；模型编辑弹窗可打开；company_admin 技术设置已隐藏；双身份切换正常；前端全量测试通过。

验收：

- system_admin 登录进入 `/ops/overview`，默认看不到新对话/知识库/精读/共享空间/治理/管理。
- system_admin 不拥有业务 caps；不能通过工作台访问公司业务内容。
- company_admin 不再看到模型/Ollama/解析/存储/集成/工作区运行设置。
- 技术配置全部可在运维工作台完成并保存成功。
- 双身份账号可从头像菜单切换，切回公司侧后按 membership 角色显示。
- 高风险操作有确认与审计记录。
- 用户目录可搜索、重置密码、授予/撤销系统管理员。
- 总览图表轮询刷新，无数据时显示空态而不是 0 或假数据。

## 3. 公司管理员（company_admin）

### 3.1 定位

公司内部的治理与管理角色：管人、管部门、看公司运营数据；不参与问答、精读、知识库、共享空间。

### 3.2 职责边界

负责：

- 成员邀请、成员角色调整、部门结构与成员归属。
- 公司治理看板与公司审计。
- 技能目录全部部门只读；创建、编辑、启停、删除与授权下放部门 manager/knowledge_admin。
- 公司治理与审计聚合数据。

不负责：

- 模型、Ollama、解析器、存储、集成、工作区运行设置；这些归 system_admin。
- 系统设置、运行队列、平台 API Key、系统审计、账号救援。

任职规则：

- company_admin 是纯公司治理身份，不兼任任何部门角色（manager / knowledge_admin / editor / viewer）；登录后不暴露部门角色，也不继承部门业务能力。即使历史数据里存在部门归属，能力计算也会忽略。
- 不进入问答、精读、知识库、共享空间；直接访问这些路由返回 403。

### 3.3 UI 形态

- 继续使用公司工作台，不新增独立驾驶舱。
- 侧边栏：只保留治理、管理；不显示新对话、知识库、精读、共享空间和历史会话。
- 治理页使用内部滚动容器，运营看板与审计日志都可上下滚动。
- 治理页：顶部页签“运营看板 / 审计日志”；company_admin 为公司看板 + 公司审计。
- 管理页：只做动作卡片；company_admin 为成员管理、部门管理；技能管理只对部门 manager/knowledge_admin 显示；治理/审计不再重复出现在管理页。
- 公司 Settings：常规、用户信息、成员、部门、技能、版本；不显示空间信息，也不显示任何技术配置或系统管理分区。
- 不展示模型/解析/队列等技术状态；技术异常由 system_admin 处理。

### 3.4 验收

- company_admin 侧边栏只有治理、管理；无问答/精读/知识库/共享空间/历史会话。
- 管理页只有成员/部门两张动作卡；技能页可进入但全部部门只读。
- 治理页可切换看板与审计。
- 直接访问问答/知识库/精读/共享空间返回 403。
- 公司 Settings 不再出现模型/Ollama/解析/存储/集成/工作区运行/系统管理。

已实施并验证（2026-10-25）：company_admin 只保留治理/管理，管理页两张动作卡；治理页“运营看板 / 审计日志”页签；business 路由 403；knowledge_admin 治理页仅看板页签。

## 4. 部门负责人（manager）

### 4.1 定位

部门业务负责人：管本部门知识库、共享、权限、技能和成员；不参与公司治理与技术运维。

### 4.2 职责边界

负责：

- 本部门知识库创建、基本信息编辑、共享管理、库内权限、文件夹管理。
- KB 设置中只保留基本信息、共享管理、库内权限；模型/解析/分块/多模态/存储/数据源等技术配置归 knowledge_admin。
- 本部门技能维护与技能编辑授权。
- 本部门成员邀请、移出部门、调整部门角色。
- 本部门运营看板与部门审计。
- 维护部门 CR 审计员名单：审计员可审批/驳回本部门所有 KB 的 CR，不能合并、关闭或改 KB。

不负责：

- 公司成员/部门结构治理（company_admin）。
- 公司看板/公司审计（company_admin）。
- 模型/解析/存储/集成/系统设置（system_admin）。
- 跨部门调动、修改公司角色、移除公司成员。

### 4.3 成员管理规则

- 只能邀请已注册用户加入本部门；邀请固定写入本部门。
- 只能调整本部门成员角色；不能改公司角色，不能操作其他部门。
- “移除”只移出本部门：清空 department_id/department_role，保留公司成员身份和账号。
- 最后一名 manager 且部门已有 KB 时，不允许降级或移出。
- 成员管理页含“成员 / 待处理邀请”两个页签，邀请只能发往本部门，只能撤销本部门邀请。

### 4.4 UI 形态

- 公司工作台；侧边栏：新对话、知识库、精读、共享空间、治理、管理。
- 治理：部门运营看板 / 部门审计两个页签。运营看板为经营 KPI + 治理待办 + 模板摘要 + 本部门 KB 健康 + 协作周转/审计摘要；不展示原始检索问题。
- 管理：成员管理、审计员、技能管理三张动作卡。
- KB 设置：manager 只看到基本信息、共享管理、库内权限；knowledge_admin 只看到基本信息与技术配置页签，无共享/ACL。
- 成员管理页：本部门成员列表、角色下拉、移出部门；待处理邀请页签可撤销。
- 审计员页：本部门成员列表 + 开关；开关增删审计员，不改成员角色。
- Settings 不出现公司成员管理；成员管理只从管理页进入。
- 不展示公司级治理、系统技术配置。

### 4.5 验收

- manager 侧栏可见共享空间/治理/管理；治理仅有部门看板与部门审计。
- 管理页为成员/审计员/技能三卡；成员页只显示本部门成员与邀请。
- 邀请其他部门返回 403；邀请本部门成功且只能撤销本部门邀请。
- 调整本部门角色成功；操作其他部门 403。
- manager 打开 KB 设置只看到基本信息/共享/库内权限，不出现模型、解析、分块等技术页签。
- knowledge_admin 可编辑技术配置；manager 通过 API 提交技术配置返回 403。
- manager 可增删本部门 CR 审计员；审计员 CR 详情返回 can_review=true，可审批/驳回，合并返回 403。
- CR 合并仅 manager 可执行。
- 部门运营台使用近 7 日检索聚合：检索量、无命中数/命中率、KB 外部检索、CR 平均周转、open issue；不记录/展示员工原始问题。
- 移出部门只清空部门归属，公司成员身份保留。
- type-check 通过，前端镜像已重建。

已实施并验证（2026-10-26）：manager 管理页两卡；部门成员页 4 人；本部门邀请 201、其他部门邀请 403；邀请撤销 200；Settings 无公司成员管理。

## 5. 知识库管理员（knowledge_admin）

### 5.1 定位

部门知识库的技术与内容维护角色：建库、配模型/解析/分块/多模态/存储、维护目录与内容、维护技能；音频处理与知识图谱已停用；不负责共享、发布、ACL 和人员。

### 5.2 职责边界

负责：

- 创建本部门知识库；不可删除知识库（删除仅 manager）。
- 模型、解析、分块、图像、高级设置、存储、数据源等技术配置；音频处理与知识图谱已停用。
- 文档内容、文件夹结构、FAQ/Gaze 等技术内容配置。
- 本部门技能维护。
- 提交/编辑 CR；被 manager 设为部门审计员或被单个 CR 指定 reviewer 时可审批/驳回，不能合并。
- 查看本部门运营看板；不看审计、成员、公司治理。

不负责：

- 共享给部门、对外发布、库内 ACL；全部归 manager。
- 删除知识库、成员/部门治理、公司审计、系统技术配置。

### 5.3 UI 形态

- 公司工作台；侧边栏：新对话、知识库、精读、共享空间、治理、管理。
- 治理：部门运营看板；无审计页签。
- 管理：知识库设置、技能管理两张卡；KB 设置从管理页选择知识库后打开，不再从知识库卡菜单进入。
- Settings：常规、用户信息、空间信息、技能管理、版本；不出现成员/部门/系统设置。
- KB 设置：基本信息 + 技术配置页签；不出现共享管理与库内权限。入口只在“管理 → 知识库设置”。
- 模型/解析/存储采用分层：system_admin 维护全局模型目录、凭据、默认值、解析引擎与存储后端；knowledge_admin 只能在 KB 内选择已启用模型/引擎/后端，并配置本 KB 的分块与规则，不能新增凭据或全局实例。
- 知识库卡菜单：不显示设置与删除；可新建/复制 KB。

### 5.4 验收

- knowledge_admin 可新建 KB、维护技术配置、文件夹与技能。
- KB 设置不出现共享管理/库内权限；DELETE KB、ACL、共享、发布 API 返回 403。
- 管理页为知识库设置 + 技能管理两卡；治理仅部门看板。
- 被 manager 加入审计员名单后可审批 CR，合并 403。
- KB 模型选择器不显示“添加模型”；解析/存储不显示跳转全局配置的快捷入口，避免越层 403。
- type-check 通过，前端镜像已重建。

已实施并验证（2026-10-26）：knowledge_admin KB 设置页签为基本信息/模型/解析/分块/图像/高级/存储/数据源；音频处理与知识图谱已移除；KB 卡菜单无设置/删除；管理页知识库设置可选择 KB 打开弹窗；DELETE KB 403；ACL GET 403；manager ACL/删除 200。

## 6. 编辑（editor）

### 6.1 定位

部门内容编辑：在已有 KB 内上传、编辑文档，参与 issue/评论和 CR 提交；不负责建库、删除、权限、人员或技术配置。

### 6.2 职责边界

- 上传、编辑本部门文档内容。

- 查看本部门技能；被 per-skill grant 授权后可编辑指定技能。
- 被 manager 加入 CR 审计员名单或被指定 reviewer 后可审批/驳回 CR。

不负责：

- 新建/复制/删除 KB，管理文件夹。
- 删除文档；删除仅 knowledge_admin/manager。
- 共享、发布、ACL、成员、部门、审计、公司治理。
- 技术配置、技能目录管理。

### 6.3 UI 形态

### 6.4 验收

- 侧栏无治理/管理；skills 页面只读，per-skill grant 后可编辑指定技能。
- type-check 通过，前端镜像已重建。

## 7. 只读成员（viewer）

### 7.1 定位

部门知识消费者：阅读 KB、检索、精读、共享空间，提交 issue/评论反馈；不生产内容，默认不参与审批或管理，被授权审计员/reviewer 时只审批、不合并。

### 7.2 职责边界

- 阅读本部门 KB 和共享入 KB，进行检索与精读。
- 评论 issue、提交 issue 反馈。
- 在问答中选择本部门已启用技能。
- 查看共享空间。

不负责：

- 上传/编辑/删除文档、建库、文件夹管理。
- 提交 CR、合并 CR。
- 默认不能审批/驳回 CR；例外：被 manager 加入部门 CR 审计员名单，或被单个 CR 指定为 reviewer 时可审批/驳回，但仍不能合并。
- 共享、发布、ACL、成员/部门、治理、审计、技术配置、技能管理。

### 7.3 UI 形态

- 侧栏只有新对话、知识库、精读、共享空间；无治理、无管理。
- KB 文档只读；无新建/删除/批量/文件夹管理入口。
- 协作页可看 issue/CR、评论和提 issue；无提交 CR 按钮。
- 被授权为部门审计员或单 CR reviewer 时，CR 详情显示审批/驳回按钮；不显示合并。
- Settings：常规、用户信息、空间信息、版本；无技能页。
- 问答技能选择器可用，但技能页不可见。

### 7.4 验收

- viewer 无治理/管理入口，KB 无编辑/删除入口。
- 可评论/提 issue，不能提交 CR。
- 默认不能审批/驳回；被加入部门审计员名单或被指定 reviewer 后可审批/驳回，合并仍为 403。
- 可选择本部门已启用技能，不能进入技能页。
- 无成员/部门/技术/审计权限。
- type-check 通过。

## 8. 权限判定与维度总表

能力码以 `contracts/capabilities.json` 为唯一事实来源；下表是角色自身的能力码，不含 `member` 基础能力。实际登录时按“公司角色 + 部门角色 + system_admin”做并集。2026-10-26 已用六个角色测试账号登录核对，返回值与本表一致。

|---|---|

- `member` 是基础；manager / knowledge_admin / editor 在 member 基础上叠加部门角色能力码；viewer 只有基础能力码。

## 9. 角色歧义裁定

### 9.1 system_admin vs company_admin

- **system_admin**：平台/技术总运维，管模型目录、凭据、解析器、存储、Ollama、集成、队列、平台 API Key、系统审计、账号救援。
- **company_admin**：公司治理，管成员、部门、公司看板、公司审计、技能目录只读。
- 单租户也不合并：company_admin 不因“公司只有一套系统”获得平台全权；system_admin 不因平台身份获得公司业务权限。
- 同一账号可以同时拥有两者，但通过不同工作台使用；入口和导航不混用，公司身份不会出现运维分区，运维身份也不会出现业务菜单。token 能力是并集，最终写操作仍由对应身份的后端守卫判断。

### 9.2 company_admin vs manager

- company_admin 不进入 KB、问答、精读、共享空间；manager 是部门业务 owner。
- company_admin 管全公司成员/部门；manager 只能管本部门成员，且“移除”是移出部门，不是移除公司账号。
- company_admin 不兼任任何部门角色（manager / knowledge_admin / editor / viewer）；公司身份不继承部门业务读写权。
- 技能：company_admin 全部部门只读；manager 本部门维护并授权。

### 9.3 manager vs knowledge_admin

- manager 是**部门业务 owner**：建库、删库、基本信息、共享、发布、ACL、成员、CR 最终合并。
- knowledge_admin 是**KB 技术与内容维护者**：可建库但不可删库；配置模型/解析/分块/多模态/存储/数据源；维护文件夹与内容。
- KB 设置入口分裂：manager 从知识库卡菜单进入（基本信息/共享/ACL）；knowledge_admin 从“管理 → 知识库设置”进入（基本信息/技术配置）。
- manager 不配置 KB 技术参数；knowledge_admin 不共享、不发布、不改 ACL、不删库。
- 两者都不是公司治理角色；均不能进入公司看板/公司审计。

### 9.4 knowledge_admin vs editor

- 都可上传/编辑文档。
- knowledge_admin 可管理文件夹、维护技术配置、删除文档；editor 不可删除文档/文件夹，不可管理技术配置。
- knowledge_admin 可维护部门技能；editor 只能查看技能，per-skill grant 后编辑指定技能。
- editor 可提交 CR；知识库管理员也可提交。两者默认均不能合并；审批需审计员/reviewer 授权。

### 9.5 editor vs viewer

- editor 生产内容：上传、编辑、提交 CR、提 issue/评论。
- viewer 消费内容：阅读、检索、精读、提 issue/评论；不能提交 CR。
- 两者都不能删除文档、建库、管理文件夹。
- CR 审批都不属于默认角色能力；两者都需要部门审计员或单 CR reviewer 授权才能审批/驳回，且都不能合并。

### 9.6 “审计员”不是审计日志角色

- 本系统中的“审计员”是 CR 审批授权：manager 可增删本部门审计员；审计员可审批/驳回本部门所有 KB 的 CR，但不能合并、关闭、改 KB。
- 审计日志是另一条能力：`audit:dept_read`（manager）和 `audit:company_read`（company_admin）；knowledge_admin/editor/viewer 无审计日志页。
- 不要把“审计员”理解为可以看部门审计日志的人；当前两套概念独立。

### 9.7 CR reviewer / 审计员 / moderator / merger

- **reviewer**：单个 CR 被指定的人，可审批/驳回该 CR；可由提交者在创建/编辑 CR 时选择，不要求部门角色。
- **部门审计员**：manager 维护的部门名单，可审批/驳回本部门所有 CR，不必逐个指派；候选为本部门任意 active 成员，不要求编辑角色。
- **moderator**：manager 在 KB 上的业务管理员权限，可审批/关闭/合并；当前也是唯一 merger。
- **合并门槛**：合并前至少一名“其他”审阅者或部门审计员批准；提交人本人的批准不计入。manager 也不能跳过审批直接合并。
- **合并**：仅 manager；审计员/reviewer 即使批准也不能合并。
- **关闭**：提交者或 manager 可关闭；审计员/reviewer 不能关闭他人的 CR。
- **审批权与角色分离**：部门审计员和单 CR reviewer 是资源级授权。viewer/knowledge_admin/editor 被授权后都能审批/驳回他人的 CR，即使其角色本身没有 `kb:content_edit`；授权不改变角色矩阵，也不带来合并权。
- **自我审批**：提交人不能审批自己的 CR，manager 也不例外。四眼原则已强制“提交人≠审批人”；是否进一步要求提交人/审批人/合并人完全三人分离仍待定。

### 9.8 KB “设置”的歧义

- 公司 Settings 弹窗：个人/账户/成员/部门/技能只读（company_admin）等，不是 KB 设置。
- KB 设置：manager 的基本信息/共享/ACL；knowledge_admin 的基本信息/技术配置。
- 全局技术设置：system_admin 的 `/ops`；knowledge_admin 只能在 KB 内选择已存在且 active 的模型/引擎/存储后端。
- company_admin 不拥有任何 KB 设置。

### 9.9 “移除成员”的歧义

- manager 的移除 = 移出本部门（清空 department_id/department_role），保留公司成员身份和账号。
- company_admin 才能邀请/移除公司成员；manager 只能邀请/移出本部门成员；system_admin 的账号救援不等于成员治理。
- 最后一名 manager 且部门已有 KB 时，拒绝降级/移出。

### 9.10 “删除”的歧义

- KB 删除：manager。
- 文档删除/批量删除：knowledge_admin、manager；editor/viewer 403。
- 文件夹删除：knowledge_admin、manager。
- 账号/成员：company_admin 可移除公司成员身份；当前没有删除用户账号的入口。system_admin 只做账号救援（创建身份、重置密码、授予/撤销系统管理员），不移除公司成员。

### 9.11 “共享/发布”的歧义

- 共享：把 KB 共享给部门，manager。
- 发布：把 KB 发布到消费者门户（visibility），manager。
- knowledge_admin 两者都没有；不能通过 KB 技术配置越权。

### 9.12 “技能”的歧义

- `skills:view`：能看到技能目录（company_admin 全部部门只读，manager/knowledge_admin 本部门，editor 本部门）。
- `settings:skills_manage`：创建/编辑/启停/删除/授权（manager/knowledge_admin 本部门）。
- per-skill grant：editor 可编辑指定 skill，不改变角色矩阵。
- viewer 不进入技能页，但问答时仍可选择本部门已启用 skill。

### 9.13 system_admin vs knowledge_admin：模型/技术设置

- **system_admin** 是供给侧：维护全局模型目录、供应商凭据、默认模型、Ollama、解析引擎、存储后端与可用状态。
- **knowledge_admin** 是消费侧：只能在本部门 KB 内选择已存在、active 的模型/引擎/后端，并配置本 KB 的分块、规则、数据源。
- knowledge_admin 不能新增供应商凭据或全局模型实例；system_admin 不编辑 KB 技术配置，也不因技术身份获得 KB 内容权限。
- KB 模型选择器不提供“添加模型”；解析/存储不跳转全局设置，避免 knowledge_admin 越层 403。
- manager 不拥有技术模型配置；editor/viewer 只能使用。

### 9.14 “统计/审计”的歧义

- 部门统计：manager / knowledge_admin；公司统计：company_admin。
- 部门审计：manager；公司审计：company_admin；系统审计：system_admin。
- CR 审阅历史存在于 CR 详情（`doc_cr_reviews`），当前不进入治理审计；治理审计记录的是 ACL/共享/成员/RBAC 等治理动作。

### 9.15 “账号运维”的歧义

- company_admin：邀请公司成员、修改公司角色/部门归属。
- manager：邀请/移出本部门、修改本部门角色，不改公司角色。
- system_admin：查询账号、创建身份、重置密码、授予/撤销系统管理员；不改成员角色和部门归属。
- 三者都不是“超级管理员”互相覆盖。

### 9.16 “模型/技能/技术”的只读例外

- system_admin 为了集成作用域可读取 KB/agent 名称、ID、计数等元数据，不读取正文或会话内容。
- company_admin 只读公司治理聚合和技能目录，不读取业务正文。
- 只读例外不等于编辑权；所有写操作仍按资源守卫。

## 10. 数据范围与资源守卫

- **租户范围**：所有角色只在其 active tenant 内计算；system_admin 通过隐式单租户上下文访问技术配置。
- **公司范围**：company_admin 可看全公司聚合/公司审计，但不进入业务正文。
- **部门范围**：manager/knowledge_admin/editor/viewer 的 KB、文档、成员、统计均使用当前部门；跨部门共享入只读。
- **KB 共享**：shared-in KB 默认只读；跨部门共享不会让接收方获得删除、共享管理或 ACL 权限。
- **ACL**：只作用于本部门 KB 的 folder/file；file 只能 deny，folder 可 allow/deny；subject 支持用户、部门、全员。deny 优先于 allow 和角色；manager 是唯一 ACL 管理角色，knowledge_admin 没有 ACL 入口。
- **CR**：reviewer/审计员授权只影响审批动作，不影响 KB 内容权限或合并。
- **API Key**：独立机器 principal；按 APIKeyGate capability + KB 白名单授权，不套用户角色；不能把 API key 当成某个员工角色。
- **判定顺序**：认证 → 路由/菜单 caps 粗筛 → 资源守卫（部门/KB/ACL/CR） → 服务层检查；前端隐藏不是安全边界。

## 12. 当前边界与后续

- “知识缺口 Top5 / 热门问题 Top5”未做：检索审计只存 query hash，不记录原始问题文本。
- 团队贡献榜暂不作为首版面板，留作进阶版。
- CR 审阅历史当前只在 CR 详情，不进入治理审计；若需公司级合规审计，需要新增事件写入。
- 合并门槛已实施：合并前至少一名其他审阅者/部门审计员批准，manager 不能跳过审批直接合并。
- 部门审计员和单 CR reviewer 当前没有角色下限：viewer 被授权后也可审批/驳回。若要求审批人必须具备编辑能力，需要在授权接口加角色校验。
- 四眼原则已强制“提交人≠审批人”；提交人、审批人、合并人完全三人分离未强制，manager 可以是审批人之一并合并。
- ACL 路由已全部收口 manager；`kb_acl` 服务内仍保留 knowledge_admin 的历史分支，不能据此认为 knowledge_admin 拥有 ACL 权限。
- 旧数据 `department_id=''` 的技能/知识库按历史数据处理；新数据必须有部门归属。
