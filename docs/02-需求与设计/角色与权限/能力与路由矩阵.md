# 能力、角色与页面路由

> 状态：当前
> 最后更新：2026-10-26
> 目标读者：前端、后端、产品、测试
> 关联：[角色生态位规定](角色生态位规定.md)、[共享空间与ACL](共享空间与ACL.md)、[部门管理工作台](../功能与交互/部门管理工作台.md)、[技能与问答注入](../功能与交互/技能与问答注入.md)

能力契约、登录 caps、路由/菜单/403、Settings 能力化、Agent 面裁剪、技能授权后端、管理工作台、治理台与 KB 设置委派均已实施；E2E 与视觉打磨属优化项。

## 1. 背景

系统存在公司角色、部门角色、KB 共享、ACL、API Key capability、部署能力等多层权限概念。页面会持续增加（管理层仪表盘、部门运营台、设置委派页等），不能把页面可见性散落在角色判断和页面内 if-else 中。

目标：把页面层级设计成能力层级的投影。路由声明所需能力，角色持有能力集合，登录/切租户时计算，菜单与路由守卫消费同一份能力定义；后端资源级守卫继续作为安全边界。

## 2. 核心原则

- 能力是现有公司角色/部门角色的**派生投影**，不是独立授权真源。
- 角色矩阵只维护一份；不为页面再维护一套角色到页面映射。
- 前端隐藏菜单是体验优化；后端守卫是规则；资源级权限是底线。
- API Key capability、部署能力与用户能力分属不同 principal/语义，不混在同一套判断中。
- 页面能力只覆盖页面/设置分区/API 入口粗筛，不细到每个按钮动作。按钮动作继续由部门角色、KB 归属、共享关系、ACL 结果判断。
- 不存在“管理页面”独立类别；管理页面就是需要治理类能力的页面。
- 不做“第二身份”。公司管理员的只读范围仅限治理聚合、审计与技能目录，不做 KB 正文只读穿透，也不是第二套 token/principal。

## 3. 能力契约

单一事实源：

```text
contracts/capabilities.json
```

结构：

```json
{
  "keys": ["kb:read", "settings:models_manage"],
  "roles": {
    "company_admin": ["..."],
    "manager": ["..."],
    "knowledge_admin": ["..."],
    "editor": ["..."],
    "viewer": ["..."]
  }
}
```

约束：

- Go 启动时加载并校验 JSON；所有 key 必须在 Go 白名单常量中。
- 前端直接 import JSON；路由 `required_caps` 只引用契约中的 key。
- 增加测试：Go 校验契约 key；前端测试校验路由 meta 不引用未知 key。
- 角色矩阵只写在该 JSON；页面不再手写角色到可见性映射。
- 共享空间部门权限、ACL、KB 访问等资源级判定不进入该 JSON。

### 3.1 能力 key 约定

统一 `domain:action`，动作用 snake_case。v1 清单：

```text
kb:read
kb:create
kb:content_edit
kb:settings_manage
kb:share_manage
kb:acl_manage
folder:manage

shared_space:view
member:view
member:manage
department:manage

settings:self_manage
settings:models_manage
settings:infrastructure_manage
settings:integrations_manage
settings:skills_manage
settings:workspace_manage
settings:system_manage

skills:view
cr:audit_manage

stats:dept_read
stats:company_read
audit:dept_read
audit:company_read
```

说明：

- `settings:infrastructure_manage` 覆盖解析器、存储、向量库、Ollama 等租户基础设施配置。
- `settings:integrations_manage` 覆盖 API、CLI 集成；IM 管理面已下线。
- `settings:system_manage` 仅 system_admin；公司管理员不拥有平台运行/系统管理能力。
- 沙箱、沙箱密钥、网络搜索、侧边栏智能体移除，不再有对应能力。
- MCP 只作为外部接入层保留；App 内 MCP 管理能力已删除。
- 技能保留；技能编辑授权是 per-skill grant，不是新的全局角色开关。

补充：

- 单租户不等于合并角色：`company_admin` 负责公司/租户治理；`system_admin` 负责部署/平台运行。两者身份分离，避免公司管理员获得平台全权。
- `system_admin` 独立持有技术配置能力：`settings:models_manage`、`settings:infrastructure_manage`、`settings:integrations_manage`、`settings:workspace_manage`、`settings:system_manage`；这些能力不从公司角色取得。
- caps = company role base ∪ department role caps；company_admin 不参与部门角色合并，也不获得任何部门业务能力。
- company_admin 不进入问答、精读、知识库、共享空间；公司治理只消费聚合统计与审计，不读取业务正文。
- 统计 `stats:dept_read` 给 knowledge_admin；审计 `audit:dept_read` 不给 knowledge_admin。
- CR 审批：manager 是 KB moderator；knowledge_admin/editor 需被指定为 reviewer 或加入部门 CR 审计员名单才能审批/驳回。审计员只审不合并，合并仅 manager。
- API Key 继续由 APIKeyGate 的 capability + KB 白名单授权，不套用户能力层。
- MCP 不再有 App 内管理能力；`settings:mcp_manage` 已删除，MCP 只作为外部接入层保留。

### 4.1 公司管理员的生态位

`company_admin` 是公司/租户内的管理与治理角色，不是平台运维角色：

- **负责**：成员与部门治理、公司看板/公司审计；技能目录全部部门只读。
- **知识库**：不进入知识库、问答、精读、共享空间；公司治理只看聚合数据。
- **部门角色**：company_admin 不可兼任部门角色；不获得任何部门业务写权限。
- **不负责**：模型/ Ollama / 解析器 / 存储 / 集成 / 工作区运行设置，系统设置、运行队列、平台 API Key、系统审计、账号救援、租户生命周期。
- `system_admin` 独立存在，负责上述技术运维与平台能力；单租户本地部署也不能把两者合并。

### 4.2 部门 skill 资源范围

Skill 归属一个部门，能力矩阵只表示“能进入技能管理/能管理技能”，具体能改哪一条由资源守卫决定：

- `manager` / `knowledge_admin`：查看、创建、编辑、启停、删除本部门 skill；不能操作其他部门。
- `company_admin`：查看全部部门 skill，全部只读；不创建、不编辑、不授权。
- `editor`：可查看本部门 skill（`skills:view`），不可编辑；被 per-skill grant 授权后可编辑指定 skill。
- `viewer`：不进入技能管理页；问答时可选择本部门已启用 skill。
- 问答选择器返回本部门已启用 skill；company_admin 不进入问答，只读技能目录，不参与 skill 选择。
- 旧数据 `department_id=''` 视为历史租户级 skill：全员可见、仅系统/无部门上下文可管理；新数据必须带部门。
- 同名 skill 只在同一部门内唯一。

## 5. 登录与租户切换

登录响应按 membership 返回能力，同时给 active tenant 一份扁平能力：

```json
{
  "memberships": [
    {
      "tenant_id": 10002,
      "role": "member",
      "department_id": "dept-10002",
      "department_role": "editor",
      "caps": ["kb:read", "kb:content_edit", "shared_space:view"]
    }
  ],
  "caps": ["kb:read", "kb:content_edit", "shared_space:view"]
}
```

规则：

- 用户在不同公司可有不同能力；切公司必须换对应 membership 的 caps。
- 前端切租户直接用 membership caps 重渲染菜单和路由；不额外请求权限接口。
- 后端每次请求按 active tenant membership + 公司角色 + 部门角色现算，不信任前端 caps。
- `system_admin` 是平台/部署身份，不进入 company_admin 能力集合；登录仍返回其独立能力。
- 能力变更（部门角色、成员状态、SKILL grant 等）在下一次登录/刷新或权限刷新时生效；高风险接口后端实时校验。

## 6. 菜单、路由与 403

### 6.1 路由声明

- Vue route meta 使用 `required_caps: string[]` 或 `required_any_caps: string[]`；默认全部满足（all-of），any 为任一满足。
- 新页面 PR 必须声明 `required_caps` / `required_any_caps`。
- 菜单项从路由树/菜单配置派生，`hasCaps(required_caps)` 不满足直接不渲染，不置灰。
- 页面内动作不使用 caps 做最终授权，继续走部门角色/KB/ACL 守卫。
- system_admin 不再绕过前端 `required_caps` / `required_any_caps`；其可访问面由登录返回的 `settings:system_manage` 等独立能力决定。

### 6.2 后端

- 新增 `middleware.RequireCapability(cap)`；按当前 membership 计算能力，缺失 403；API Key 仍由 APIKeyGate 短路。
- 当前只给管理页、设置分区、系统管理、技能、统计/审计等新面挂 caps。
- KB、文档、ACL、协作等现有路由继续保留资源级守卫，不要求一次性迁移全部路由。
- 同一份 `capabilities.json` 是前后端 key 的单一事实源。

### 6.3 403 UI

- 增加全局 `/403` 页面：说明缺少哪项能力、可读名称、返回我的工作台、可选申请权限入口。
- 路由守卫失败跳 `/403?required=...&from=...`。
- API 403：
  - 页面已有内容时只提示，不强制跳走，避免丢草稿。
  - 初次进入/页面级 API 失败可跳 `/403`。
- Settings 无权限直接使用统一 403，不再维护独立 role-denied 面板。
- 菜单未授权项隐藏；403 不暴露资源是否存在。

### 6.4 管理工作台

管理能力不再散落在左下角头像菜单，也不逐项平铺成侧边栏一级项。

- 侧边栏保留“治理”，其后增加单一“管理”入口；仅当用户持有任一管理能力时显示。
- `/platform/management` 为管理动作页：company_admin 为成员、部门；manager 为成员、审计员、技能；knowledge_admin 为知识库设置、技能；治理台与审计移到“治理”页签，不再重复。
- `/platform/governance` 为治理页：公司/部门按 `stats:*` 选择看板，`audit:*` 决定是否显示审计页签。
- 成员、部门卡跳转对应设置/成员页；技能写权限只给部门 manager/knowledge_admin。
- KB 设置页签：manager 只保留基本信息、共享管理、库内权限；模型/解析/分块/多模态/图谱/存储/数据源等技术配置只给 knowledge_admin。
- 头像菜单只保留个人设置、空间设置、全部设置；不再重复成员/模型/技能/系统管理快捷项。
- system_admin 使用独立 `/ops` 运维工作台，不进入公司管理工作台；登录默认落地 `/ops/overview`。
- 双身份 system_admin 可从运维台头像菜单切换到公司工作台；公司侧按 membership caps 计算，system_admin 能力不穿透。

## 7. 公司管理员只读治理

company_admin 始终是同一身份，不进入业务页面。

- 只进入治理与管理：治理看板、审计、成员、部门。
- 问答、精读、知识库、共享空间、历史会话不显示，直接访问返回 403。
- 治理只消费聚合统计与审计，不读取业务正文；治理数据只读。
- 不新增 token、不新增 principal；`principal_kind` 仍区分 member/company_admin/portal。
- 不造第二身份，也不通过部门角色获得业务写。

## 8. 设置委派

### 8.1 归属

- 个人设置：所有成员。
- 公司设置：company_admin 负责成员、部门、公司治理；技能目录只读查看，写入下放部门；技术配置由 system_admin 在公司运维工作台管理。
- 知识库内设置：manager / knowledge_admin；shared-in 只读。
- 模型、Ollama、解析器、存储、集成、工作区运行设置统一归 system_admin；不再留在公司 Settings 弹窗。
- 不新增“部门级设置页”；需要时另立设计，不把设置分区能力直接下放。

### 8.2 设置分区

公司 Settings 弹窗：

| 设置分区 | 能力 |
|---|---|
| 常规、用户信息、我的记忆 | `settings:self_manage` |
| 成员、部门 | `member:manage` / `department:manage` |
| 技能 | `skills:view` 进页；写操作另需 `settings:skills_manage` |
| 版本信息 | `settings:self_manage` |

运维工作台 `/ops/*`：

| 分区 | 内容 | 能力 |
|---|---|---|
| 模型与引擎 | 模型、Ollama、解析器、存储 | `settings:models_manage` / `settings:infrastructure_manage` |
| 集成 | API、CLI | `settings:integrations_manage` |
| 运行队列 | 队列、worker/模型并发 | `settings:system_manage` / `settings:workspace_manage` |
| 安全与审计 | 平台 API Key、系统审计、网络安全 | `settings:system_manage` |
| 账号运维 | 用户目录、创建、重置密码、系统管理员授权 | `settings:system_manage` |
| 系统设置 | 空间默认值、工作区运行、版本 | `settings:system_manage` / `settings:workspace_manage` |

### 8.3 Agent 面裁剪

移除：

- 侧边栏“智能体”入口。
- 内部 Agent 编辑器/Agent 路由/Agent 相关前端能力；MCP 外部 Agent 接入保留。
- Settings：沙箱配置、沙箱密钥、网络搜索。

保留：

- MCP：后续外部 Agent 接入知识库的协议入口。
- 技能：维护 `skill.md`。
- API/CLI 集成。
- 知识库、模型、解析、存储、向量库、成员、部门、审计。

## 9. 能力路由交付

1. `contracts/capabilities.json` + Go/前端双端加载与校验。
2. 登录响应 membership caps + active tenant caps。
3. 前端 `required_caps`、菜单过滤、统一 `/403`。
4. 后端 `RequireCapability`，只挂新管理面/设置分区。
5. Settings 分区能力化；移除沙箱/沙箱密钥/网络搜索/侧边栏智能体；保留 MCP/技能。
6. 技能目录权限与 per-skill 编辑授权后端。
7. 测试：未知 key、角色矩阵、membership caps、403、菜单过滤、资源守卫不回退。

## 11. 验收

- 新页面只改 route meta + capabilities.json，不改页面内角色 if-else。
- 未授权菜单不渲染；手输 URL 进统一 403；API 403 不产生越权数据。
- 多公司用户切换公司后菜单/页面能力正确变化。
- company_admin 不进入 KB 正文；只读仅限治理聚合、审计与技能目录，不具备业务写/共享/ACL 能力。
- 管理角色只有一个“管理”入口；卡片按 caps 裁剪，头像菜单不重复管理快捷项。
- system_admin 不进入公司管理工作台；技术配置与系统设置只能在 `/ops` 运维工作台访问。
- 沙箱/沙箱密钥/网络搜索/侧边栏智能体不再出现；MCP 与技能保留。
- 未知能力 key 在 Go/前端测试中失败。
